# Build Plan

Companion to [`prompts/full.md`](../prompts/full.md), the phase-by-phase spec fed to Codex. That file is the source of truth for *what* to build in each phase; this file is the project-tracking view — one row per phase, in build order, with the exit criteria and open decisions that don't belong in the spec itself.

The backend/API is specced in `prompts/full.md`; the web client (`apps/web`) has its own phase-by-phase spec in [`prompts/web.md`](../prompts/web.md), numbered `WEB PHASE 0`–`17` to shadow the API phases it consumes. See [Web UI build plan](#web-ui-build-plan) below.

Two decisions locked in during spec review (2026-09-01), both reflected in `prompts/full.md`:

- **Hosting model**: the app never operates its own PDS. Users bring their own AT Protocol identity; public records are written to *their* repo via OAuth-scoped writes, never to an app-controlled one.
- **Content policy**: adult/NSFW creator content is in scope. This rules out assuming Stripe as the eventual `PaymentProvider`/`PayoutProvider`, and pulls creator KYC/age-verification forward from "future work" to a gating design requirement (Phase 14, enforced starting Phase 6's payout onboarding).

Each phase below ends with the standard exit checklist from `prompts/full.md`: tests pass, lint passes, type check passes, app starts, README updated, `docs/architecture.md` updated, files-changed summary, known limitations documented, next phase identified. Not repeated per-row.

**Phase 11 (AT Protocol Spaces) has been extracted** from `prompts/full.md` / `prompts/web.md` into `prompts/atproto-spaces.md` and now runs **dead last** — after Phases 12–17 and after the two rearchitecture specs (`prompts/creator-owned-pds.md`, then `prompts/bluesky-public-posts.md`). Slot 11 is left vacant, not renumbered. Phase 4 wires `fans.foryour.profile` into real routes for the first time (`POST /creators`, `PATCH /creators/me`) with AT-write-before-DB-write ordering, slug validation/cooldown, and ownership-by-construction (`/creators/me` never accepts a creator id from the client) — 15 route tests plus a caught-and-fixed real bug (the slug-change cooldown originally blocked a creator's very first edit). `/become-a-creator`, `/creator/settings`, `/c/[slug]` are live. Phase 5 adds `SubscriptionTier` CRUD (`POST/PATCH/DELETE /creators/me/tiers`, `GET /creators/:creator/tiers`) with the same AT-write-first discipline, reusing one generated `tid` rkey across a tier's updates/deletion rather than minting a new one each time — 16 route tests + 8 pure-validation unit tests, plus a mid-phase architecture correction (tier domain logic moved from `apps/api` into `packages/subscriptions`, and the AT-record injection types into `packages/atproto`, once it became clear a package can't depend on an app). The Lexicon namespace was also renamed from the `dev.creator` placeholder to the real `fans.foryour` (reverse-DNS of the now-selected production domain, `foryour.fans`) — zero-migration since nothing had been published under the placeholder yet. Phase 6 builds `PaymentProvider`/`PayoutProvider` interfaces (hosted-checkout shape: `createSubscription` returns `{status: "pending"|"active", redirectUrl?}` rather than assuming synchronous confirmation) plus fake implementations wired as the real Phase 6 code (never a real processor — real money must never move through them), `Subscription`/`PaymentEvent`/`PayoutAccount` models entirely in Postgres (never AT Protocol — see docs/atproto-vs-database.md), idempotent webhook processing (`PaymentEvent` ledger keyed by `[provider, providerEventId]`, verified by a real replay test), and an entitlement service (`canAccess`, using `SubscriptionTier.sortOrder` as an inferred tier hierarchy pending Phase 7 confirmation) — continuing Phase 5's package-boundary discipline (`packages/subscriptions` owns the domain logic, `apps/api` routes stay thin). Two real test-hygiene bugs were found and fixed along the way: a hardcoded webhook event ID that collided across isolated vs. full-suite runs, and a genuine cross-file test-handle collision (`"liam.test"` used in both `creators.test.ts` and `subscriptions.test.ts`) that caused nondeterministic failures under vitest's parallel file execution — fixed with a `uniqueHandle()` helper, documented in docs/architecture.md. Phase 7 builds `ContentRepository` (storage-only by design — entitlement checking stays outside it, in `apps/api/src/routes/posts.ts`, per `canAccess`'s own Phase-6-era doc comment promising exactly that) and `PrivateContentRepository` in a new `packages/content`, plus the `Post`/`PostMedia` Postgres models. Only `PUBLIC`-visibility posts get a mirrored `fans.foryour.post` AT record (reusing the same mint-once/reuse-rkey/retract-on-leaving-PUBLIC discipline Phase 5 established for tiers); `SUBSCRIBERS`/`TIER` posts never touch the AT network at all. `updatePost` is fully implemented (including the visibility-crossing publish/retract transition logic) despite Phase 7 defining no HTTP route for it — spec's route list has no `PATCH` — so it's covered by direct repository tests instead of route tests. The required (but intentionally unfinished) `AtprotoSpacesContentRepository` stub is also in place, wired nowhere. All 5 of the spec's access-control test cases pass (anon, non-subscriber, valid subscriber, wrong-tier, creator-self), exercised through the real subscribe+webhook HTTP flow, not hand-inserted rows. Phase 8 builds `ObjectStorage` (`packages/media`, deliberately storage-only, same discipline as `ContentRepository`) with `S3ObjectStorage` as the real, only implementation — unlike Phase 6's fakes, object storage has no business-decision blocker (MinIO is already a real running S3-compatible target), so it's genuinely wired against local MinIO in `server.ts`, and verified with a real presigned-URL PUT/GET/delete round trip against it (byte-for-byte match, 404 confirmed after delete) — the Phase 8 analogue of Phase 2's live-network check. `MediaAsset`'s `PENDING_UPLOAD → PROCESSING → READY/REJECTED` lifecycle is driven by an injected `MediaProcessor`; `PassthroughMediaProcessor` (always "ready", no real scanning) is the real Phase 8 implementation, with the interface itself being the hook Phase 14's real scanner plugs into. `GET /media/:id/access`'s entitlement rule (creator-always, else any active subscriber at any tier) is narrower than a post's because Phase 8 doesn't attach a `MediaAsset` to a specific `Post` yet — `PostMedia` gained a real FK to `MediaAsset` but still has no writer. Along the way, a real, previously-undetected gap surfaced: `apps/api`'s `pnpm typecheck` had never covered `test/` (only `src`) since Phase 1, silently — fixed with a dedicated `tsconfig.typecheck.json`, which immediately surfaced (and let a fix be verified against) real errors at every `buildApp()` call site needing the new options. A rare (~4%), unreproduced test flake was also observed and honestly documented rather than papered over with a guessed fix. Phase 9 builds `GET /feed` (the home feed) and `GET /creators/:creator/feed` (a per-creator feed). Since no `Follow` model exists anywhere in `prompts/full.md`'s 17 phases, "public posts from followed/discovered creators" reads as "every `PUBLIC` post platform-wide" — a faithful reading, not a shortcut, since `PUBLIC` already means visible to anyone. `ContentRepository` grew a sixth method, `getFeed` (an unfiltered candidate set, same storage-only discipline as the original five), with real entitlement filtering staying in `apps/api/src/routes/feed.ts` via the same `checkPostAccess` Phase 7 built (exported and reused, not re-implemented). `GET /feed` has `?limit=` only (an honest, documented over-fetch-and-slice, not a strict-guarantee retry loop, since Phase 9's own spec text doesn't ask for cursor pagination); `GET /creators/:creator/feed` gets real cursor pagination, since it never drops a row — an inaccessible post becomes a safe `{id, visibility, createdAt, requiredTier, locked: true}` stub instead of being omitted. Phase 10 builds a new `packages/discovery`: `JetstreamIngestor` (a resilient WebSocket client, own reconnect/backoff, own `apps/api/src/ingest.ts` process — deliberately separate from `server.ts` so N HTTP replicas don't each re-consume the same firehose), a commit-event parser + indexer feeding `IndexedCreatorProfile`/`IndexedPost`/`IndexedTier` (DID-keyed, covering any DID publishing `fans.foryour.*` records, not only ones registered here), and `GET /discover`/`GET /search`. The spec's own "research current mechanisms" instruction paid off directly: doc-based research described a "v2" Jetstream wire format, but connecting to the real live production endpoint showed it actually serves the older flat v1 shape (`{did, time_us, kind: "commit", commit: {...}}`) with a `wantedCollections` query param (not `collections`, which the real server silently ignores rather than erroring on) — `packages/discovery` is built against the verified-real format, confirmed by a live `JetstreamIngestor` connecting to production and processing hundreds of real events end-to-end (not just the raw parser). A second, real cross-file test race was found and fixed the same day (three new `packages/discovery` test files sharing a table, one file's blanket `afterEach` deleteMany wiping another's in-progress test data) — same root cause as Phase 6's handle-collision bug, fixed the same way (scope cleanup to specific dids, never a blanket wipe). 294 tests total across the workspace. Phases 12–17 not started; the old Phase 11 (Spaces) is extracted to `prompts/atproto-spaces.md` and runs dead last.

## Known deliberate gaps (not scheduled in any phase above)

Carried over from the spec review — intentionally out of scope of `prompts/full.md`, called out so they aren't mistaken for oversights later:

- **Transactional email/notifications** (receipts, cancellation confirmations, payout failures, moderation notices). Needed before real-money production launch; not in any phase.
- **Real payment/payout processor selection.** Phase 6 builds the abstraction and a fake implementation only; picking an actual adult-content-compatible processor is a business decision, not a Codex phase.
- **Video transcoding, thumbnailing, virus/moderation scanning implementations.** Phase 8 designs the interface (`MediaProcessor`) and status lifecycle (`PENDING_UPLOAD→PROCESSING→READY`/`REJECTED`), shipping `PassthroughMediaProcessor` (always "ready", no real scanning) as the real implementation. Phase 14 (Trust and Safety Foundation) built the *human-review* pipeline this plugs into (`Report`/`ModerationCase`/`ContentLabel`/admin actions) plus a separate, analogous automated-classifier hook for report triage (`ContentClassifier`, also passthrough-only — see `docs/architecture.md`'s Phase 14 section) — but did not implement real media scanning/transcoding itself, nor wire a classifier into the upload path. `PassthroughMediaProcessor` is still the only `MediaProcessor` implementation; a real scanner remains a future, undetermined phase's job, plugging into the same interface with zero schema change.
- **Frontend/e2e test tooling** (e.g. Playwright). `prompts/full.md` only requires API-level tests; `prompts/web.md` fills this gap — Vitest + React Testing Library from `WEB PHASE 0`, Playwright from `WEB PHASE 2` once the auth flow exists.

## Out-of-band refactor: Handle as Identity ([`prompts/handle-identity.md`](../prompts/handle-identity.md))

Runs **after PHASE 7 / WEB PHASE 4, before PHASE 8 / WEB PHASE 5** — its own session(s), backend then web. It removes the `Creator.slug` PHASE 4 introduced (an app-owned vanity string layered on portable identity — the only such name in the system). After it: the **AT handle is the public identity** for every user, the **DID is the durable key**, the creator page is `/c/<handle>` (and `/c/<did>`, which never breaks), a changed handle 301-redirects old `/c/<oldhandle>` links via a new `CreatorHandleHistory`, and `POST /creators` takes profile fields only. `prompts/full.md` PHASE 8+ and `prompts/web.md` WEB PHASE 5+ already assume no slug exists; PHASE 4 / WEB PHASE 4 carry a "partly superseded" note.

**Backend refactor done (2026-09-02).** Migration `20260902020000_handle_as_identity` drops `Creator.slug` / `slugUpdatedAt` and their unique index, adds `CreatorHandleHistory` (`creatorId`, denormalized `did`, `previousHandle`, `recordedAt`; `@@index` on `previousHandle` and `did`). `apps/api/src/services/creators.ts` lost every slug symbol (`SLUG_PATTERN`, `RESERVED_SLUGS`, `validateSlug`, the `Slug*Error` classes, the 7-day cooldown); `POST /creators` and `PATCH /creators/me` are profile-only. New `resolveCreatorByIdentifier` returns `found` / `moved` / `not-found`; `GET /creators/:identifier` answers a former handle with `301 { movedTo, did }` + `Location`. `syncUserFromProfile` (`packages/auth`) appends a `CreatorHandleHistory` row when it overwrites a creator's handle at login — no new hot-path network calls. `SubscriptionWithContext` / `/subscriptions` now carry `creator.handle` instead of `creator.slug`.

**Web refactor done (2026-09-02).** `/become-a-creator` is a 3-step wizard (Profile → Content rating → Review); the Slug step, `apps/web/lib/slug.ts`, `lib/useSlugAvailability.ts` and their tests are gone. `app/(marketing)/c/[slug]` → `app/(marketing)/c/[handle]`; the page handles `200` (render), `301 {movedTo}` (a former handle → `permanentRedirect('/c/<movedTo>')`, an HTTP 308) and `404`. `/creator/settings` lost the `SlugChangeDialog`; its Page-address card is a static note (address follows the AT handle; `/c/<did>` never changes). `lib/session.ts#OwnCreatorSummary`, the dashboard and become-a-creator redirects all key on `handle` (falling back to `did`). - [`prompts/creator-owned-pds.md`](../prompts/creator-owned-pds.md) — **rearchitecture.** foryour.fans stops being the system of record for creator content. Creator profiles, tiers, posts, media, and creator-authored config become records/blobs in the *creator's own PDS*; gated (subscriber/tier) content is **encrypted** before it is written there, with foryour.fans coordinating payment → entitlement → decryption-key grants. Postgres/S3 are demoted to caches and rebuildable indexes (`isAuthoritative: false`, `sourceUri`, `indexedAt`, `cacheExpiresAt`). Expands the lexicon set: adds `fans.foryour.media`, `fans.foryour.accessPolicy`, `fans.foryour.serviceConfig`, plus gating/linkage fields on `fans.foryour.post`. Self-gated: "stop and defer" if encrypted-PDS storage can't be made safe with today's protocol surface — ship public creator-owned content only, leave paid/private behind a documented protocol gap, and do **not** keep app-owned storage as the permanent design.
- [`prompts/bluesky-public-posts.md`](../prompts/bluesky-public-posts.md) — **refactor (implemented, flag-gated).** Every `PUBLIC` post authored here is dual-published to the creator's PDS as **both** `app.bsky.feed.post` (so Bluesky and compatible clients render it) **and** `fans.foryour.post` (fan-service metadata), linked by AT URI/CID (one-way, custom → Bluesky). Feeds and discovery merge the two into one item and dedupe. Gated posts are never written as `app.bsky.feed.post`. Still requires `CREATOR_OWNED_PDS_ENABLED`; media bytes to the PDS still deferred.
- [`prompts/atproto-spaces.md`](../prompts/atproto-spaces.md) — **experimental, extracted.** The old Phase 11 / WEB PHASE 11 Spaces adapter (`AtprotoSpacesContentRepository`, `SpaceAuthority`, `ATPROTO_SPACES_ENABLED=false`, dev-only `/dev/spaces`), pulled out of the numbered sequence so the main build has no experimental detour. Runs dead last. By the time it runs, `creator-owned-pds.md` has already made gated content encrypted and creator-PDS-owned, so Spaces is a **key-grant / permission transport** over that storage — never the storage backend — with `canAccess` still the sole authority.

**Order confirmed (2026-09-02): `creator-owned-pds.md`, then `bluesky-public-posts.md`, then `atproto-spaces.md` — dead last.** Pinned in the `prompts/full.md` and `prompts/web.md` preambles. Rationale for the first two: the PDS pivot redraws the lexicon shape and moves where posts live; once `fans.foryour.post` already resides on the creator's PDS, dual-publish is just "also write `app.bsky.feed.post` next to it." Reverse them and the dual-publish plumbing gets built against app-owned storage and reworked when storage moves. Escape hatch: `creator-owned-pds.md` gates itself on a privacy review; if that stalls, `bluesky-public-posts.md` is lower-risk and can still ship against today's architecture on its own. Spaces is last because it is experimental and, post-pivot, only makes sense layered on encrypted creator-owned storage.

**Status (2026-09-03): Phase 12 (Comments, Likes, Social) done.** New `Comment`/`Like` Postgres models (migration `20260903151513_add_comments_and_likes`) and two new `packages/content` modules (`comments.ts`, `likes.ts`) — Postgres-only, never mirrored to AT Protocol for any post visibility (a uniform rule, not visibility-dependent — see `docs/architecture.md`'s Phase 12 section for why). `POST`/`GET /posts/:id/comments` and `POST`/`DELETE /posts/:id/likes` (`apps/api/src/routes/comments.ts`/`likes.ts`) share one new helper, `loadAccessiblePost` (`apps/api/src/routes/posts.ts`), which reuses `GET /posts/:id`'s own `checkPostAccess` entitlement gate so "access inherited from the parent post" is one implementation, not per-route logic — a denied caller gets a real `403` (`GET /posts/:id`'s locked-stub `200` doesn't apply here; there's no safe partial view of a comment thread).
