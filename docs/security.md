# Security

Phase 15 (Production Hardening) deliverable — `prompts/full.md` PHASE 15 asks for a production-readiness pass across authentication, authorization, media security, billing, the database, the API layer, and observability, plus this document, `docs/threat-model.md`, and `docs/production-readiness.md`. This file describes **what the system actually does today** to protect itself, with file references so a reviewer can verify each claim against the code rather than trust prose. It is not a policy document and it does not invent legal/compliance requirements — see `docs/architecture.md`'s Phase 14 section and "Legal/compliance review required" below for what is explicitly out of scope.

## Authentication

AT Protocol identity is the only identity system (`prompts/full.md` "Core product idea" — no parallel username/password auth exists anywhere in this codebase).

- **OAuth flow.** `POST /auth/atproto/start` (`apps/api/src/routes/auth.ts`) calls `@atproto/oauth-client-node`'s `NodeOAuthClient.authorize()`, which performs a Pushed Authorization Request (PAR) to the target PDS/authorization server. PKCE is mandatory in that library for every authorization request (not optional, not something this app's code could accidentally disable) and `dpop_bound_access_tokens: true` is set in the client metadata (`packages/atproto/src/oauthClient.ts`) — every issued token is DPoP-bound to a private key this process holds, not a bearer token a stolen HTTP log or proxy trace could replay.
- **OAuth state (CSRF on the login flow itself, a.k.a. "login CSRF").** The `state` value the AS returns on callback is validated against `createRedisStateStore`'s (`packages/auth/src/atprotoStores.ts`) server-side record of the specific flow that was started, with a 10-minute TTL. An attacker cannot forge a `state` that matches a stored PKCE verifier for a flow they didn't initiate, so they cannot force a victim's browser to complete a login bound to an attacker-controlled account (the classic "login CSRF" attack). The 10-minute TTL bounds how long an abandoned flow stays exploitable at all.
- **Application session.** `createAppSession`/`getAppSession`/`destroyAppSession` (`packages/auth/src/appSession.ts`) are a from-scratch, Redis-backed session store deliberately separate from the AT OAuth grant (`AtprotoOAuthSession`, Postgres — the DPoP-bound token material `NodeOAuthClient` needs to act on a DID's behalf later). The cookie carries only an opaque 32-byte, base64url-encoded session ID (`generateToken()`) — no JWT, no claims a client could tamper with; every field the server trusts (`did`, `csrfToken`, `createdAt`) lives server-side and is revocable by deleting one Redis key. A brand-new random session ID is minted on every successful login (`createAppSession` is called fresh in the OAuth callback, never reused across logins), which is the standard mitigation for session-fixation: an attacker who tricks a victim into using a pre-chosen session ID gains nothing, because login always replaces it.
- **Cookie settings** (`apps/api/src/routes/auth.ts#sessionCookieOptions`/`csrfCookieOptions`): `httpOnly: true` on the session cookie (never readable from JS — defeats a large class of XSS-driven session theft), `secure: true` in production (never sent over plain HTTP), `sameSite: "lax"` (sent on top-level navigation but not on cross-site subrequests/form posts, the standard CSRF-hardening default that doesn't break the OAuth-redirect login flow the way `sameSite: "strict"` would), and a `path: "/"` scope with a 30-day `maxAge` matching `APP_SESSION_TTL_SECONDS`. The CSRF cookie is deliberately **not** `httpOnly` — see CSRF below — but shares every other setting.
- **CSRF (on already-authenticated requests).** Double-submit pattern: `requireCsrf` (`apps/api/src/plugins/session.ts`) 403s unless the `x-csrf-token` request header matches the *server-side* session record's `csrfToken` — not the cookie value directly, so a same-site attacker who can merely set a cookie (but not read the response or run JS) cannot forge a match. Every state-changing route (`POST`/`PATCH`/`DELETE`) requires both `requireSession` and `requireCsrf`; the only intentional exception is `/webhooks/:provider`, which is never called by a browser and is verified a different way (see Billing below).
- **Session theft.** The session ID's only path to an attacker is XSS (defeated in the ordinary case by `httpOnly`) or network interception (defeated by `secure` + TLS in production). There is deliberately **no** IP- or User-Agent-binding of a session: AT Protocol's whole premise is a portable identity used from many devices/clients, and binding a session to a single IP would break normal mobile/Wi-Fi roaming while providing weak protection (both are trivially spoofable by a real attacker). This is an accepted trade-off, not an oversight — see `docs/threat-model.md`.
- **Session rotation.** A privilege change (`User.role` → `ADMIN`, `User.status` → `RESTRICTED`, `Creator.verificationStatus` → `VERIFIED`) never needs session rotation because none of those mutable fields are ever cached on the session cookie or in the Redis session record — `requireAdmin`/`requireNotRestricted` (`apps/api/src/plugins/session.ts`) and every entitlement check re-read the current row from Postgres on every request. A demoted admin or a newly restricted user loses access on their very next request without any session being invalidated.

## Authorization

Every `/creators/me/*`, `/media/*` (owner-scoped), and `/creators/me/tiers/*`/`/posts/*` route resolves the acting creator via `prisma.creator.findUnique({ where: { did: request.session!.did } })` — **ownership by construction**: there is no route anywhere in this codebase that accepts a client-supplied creator/user id for a `/me/*`-style operation and then separately checks it belongs to the caller. A parameterized id (`:tierId`, `:id`, `:identifier`) is always looked up scoped to the already-resolved owner (e.g. `getOwnedTier(prisma, creator.id, tierId)`, `getOwnedMediaAsset(prisma, creator.id, id)`), so a nonexistent-or-not-yours id and a genuinely nonexistent one are indistinguishable to the caller (both `404`) — see "Information disclosure" in `docs/threat-model.md` for why that's deliberate.

- **Subscription entitlement** is centralized in one function, `canAccess` (`packages/subscriptions/src/entitlements.ts`), reused by `checkPostAccess` (`apps/api/src/routes/posts.ts`) for posts, comments, and likes, and again by `GET /media/:id/access` for media. There is exactly one place "does this DID have paid access to this creator/tier" is decided; every gated read goes through it.
- **Admin routes** (`apps/api/src/routes/admin.ts`) all require `requireAdmin(prisma)`, which re-reads `User.role` from Postgres on every call (never trusts the session cookie) — a demoted admin loses console access immediately, not at next login.
- **Restricted-account gating** (`requireNotRestricted`) is applied to every write capable of harming another user or the platform: commenting, liking, subscribing, filing a report, blocking (both the generic `POST /blocks` and, since Phase 15, `POST /creators/me/blocks` — see "Findings and fixes" below). It intentionally does not block reading, unliking/unblocking, or a restricted user's own existing content/subscriptions.
- **A dedicated audit pass of every route file not covered above** (`comments`, `likes`, `feed`, `contentKeys`, `reports`, `blocks`, `creatorBlocks`, `verification`, `admin`, `discovery`, `dashboard`, `webhooks`, `health`, `ready`) was run for this phase, checking every route's preHandlers, every client-supplied id for an ownership check, admin gating, and restricted-user gating. See "Findings and fixes" below for the one real gap it found.

### Findings and fixes (this phase)

- **`POST /creators/me/blocks` was missing `requireNotRestricted`.** Every other route capable of harming another user (`POST /blocks`, commenting, liking, subscribing, reporting) already had it; a creator-block is the same category of action (unilaterally cutting a user off from a creator's content/comments) and a restricted creator could still take it. Fixed in `apps/api/src/routes/creatorBlocks.ts`; regression test in `apps/api/test/creatorBlocks.test.ts` ("403s a restricted creator's attempt to file a new creator-block") and an added assertion in `apps/api/test/admin.test.ts`'s existing restrict-account test. `DELETE /creators/me/blocks/:identifier` (unblocking) is deliberately left ungated, matching `DELETE /blocks`'s existing precedent — undoing a block never harms anyone.
- **`ContentKeyGrant.subscriptionId` had no foreign key** — a bare `String? @db.Uuid` column with an index but no `@relation`, meaning nothing at the database level stopped it from pointing at a nonexistent `Subscription` row (application code always populates it correctly today, but the schema didn't guarantee it). Added a real relation with `onDelete: SetNull` — see `docs/architecture.md`'s Phase 15 section and the "Database" section below.

## Production deployment guards

`prompts/security-hardening.md` — a standalone pre-existing hardening spec this repository had never actually run — flagged three concrete issues from a static review: (1) `apps/api/src/server.ts` wired `FakePaymentProvider`/`FakePayoutProvider` unconditionally with no guard against production use, while `FakePaymentProvider.handleWebhook` does no real signature verification (a forged `/webhooks/fake` delivery could activate a `PENDING` subscription in any environment exposed to other users); (2) `GET /media/:id/access` authorized by "any active subscription to the creator," broader than post-level entitlement; (3) `CREATOR_OWNED_GATED_CONTENT_ENABLED` (documented as not production-safe) had no `NODE_ENV=production` guard. Issue (2) was already resolved by the time Phase 15 ran (`GET /media/:id/access` now requires passing the exact same `checkPostAccess` gate as the specific post(s) an asset is attached to — see Media security below); this phase closes (1) and (3):

- **`apps/api/src/config/env.ts` now refuses to boot with `NODE_ENV=production` and `PAYMENT_PROVIDER=fake` or `PAYOUT_PROVIDER=fake`.** These are new, explicit, typed env fields (`z.enum(["fake"])` today — the enum grows the day a real provider is chosen) driving `server.ts`'s provider construction, replacing the previous unconditional `new FakePaymentProvider()`. There is deliberately **no break-glass override** — per `prompts/security-hardening.md`'s own preference ("prefer no break-glass variable unless deployment workflows genuinely require one") and because the honest state of this project is that it is not deployable for real money yet; a bypass flag would just be a footgun with an extra step.
- **The forged-fake-webhook risk is closed in two layers.** In a *production* deployment it is closed by construction: `PAYMENT_PROVIDER=fake` can never boot under `NODE_ENV=production`, so `paymentProvider.name` is never `"fake"` and `/webhooks/fake` (gated by `provider === paymentProvider.name` in `apps/api/src/routes/webhooks.ts`) does not route at all. But `NODE_ENV=development` is a legitimate *deployed* configuration — the staging overlay runs it against a real public `PUBLIC_URL` to exercise hosted AT OAuth — and there the fake provider (and its unsigned webhook) is live. For that case, `ALLOW_FAKE_WEBHOOKS` (`apps/api/src/config/env.ts`, default `true`) lets such a deployment shut the route: when it is `false`, `webhooks.ts` returns the same opaque `404` for the fake provider as for an unknown one. `infrastructure/kubernetes/overlays/staging/api-env-config.yaml` sets it `false`; local dev / CI / the test suite leave it unset. Covered by `apps/api/test/subscriptions.test.ts` ("404s a well-formed fake delivery, with no effect, when `ALLOW_FAKE_WEBHOOKS` is off"). A real, signature-verifying provider is unaffected by the flag.
- **`CREATOR_OWNED_GATED_CONTENT_ENABLED=true` under `NODE_ENV=production` is now also a startup failure**, independent of the provider checks above — a platform could in principle reach production readiness for subscriptions before a dedicated security review approves gated creator-owned content (offline ciphertext exposure risk, Spaces still alpha — see `docs/creator-owned-pds.md`).
- All three guards are `zod` `.refine()`s on the existing env schema, tested in `apps/api/test/env.test.ts` (production rejects each; development/test still boot with fakes, unchanged).

## Media security

`GET /media/:id/access` (`apps/api/src/routes/media.ts`) is the sole path to a signed download URL for private media, and it re-checks entitlement on **every call** — it never caches or trusts a prior "yes." The rule, unchanged from Phase 8/WEB PHASE 8 but re-verified this phase with an explicit bypass-attempt test suite (`apps/api/test/media.test.ts`, 23 tests):

- the asset's own creator can always fetch their own `READY` asset;
- otherwise, the viewer must pass the exact same `checkPostAccess` gate `GET /posts/:id` uses, against **every** post the asset is attached to (so a TIER-gated post's media requires a sufficient-tier ACTIVE subscription, a PUBLIC post's media is open to anyone);
- an asset attached to no post at all is creator-only (never leaks to a subscriber);
- a non-`READY` asset (`PENDING_UPLOAD`/`PROCESSING`/`REJECTED`) never yields a signed URL, even to its own creator.

Signed URLs themselves (`packages/media/src/s3Storage.ts`) are short-lived — 60 seconds for a download, 5 minutes for an upload — and scoped to one object key each via the AWS SDK's own presigning (`getSignedUrl`), so a leaked URL is useless within a minute and can never be edited to address a different object.

**Verified this phase, with a dedicated test for each:** a lower-tier subscriber cannot access higher-tier-gated media (existing coverage); an anonymous/non-subscribing caller cannot access gated media (existing coverage); one creator cannot complete or access another creator's upload (existing coverage); and — new this phase — **a subscriber loses media access the instant their subscription lapses**, not just at the next page load: `apps/api/test/media.test.ts`'s "a subscriber loses media access the instant their subscription lapses (payment failure)" delivers a `payment.failed` webhook mid-test and re-asserts `GET /media/:id/access` on the exact same asset now returns `403`.

## Billing

`packages/subscriptions/src/webhooks.ts#processWebhookEvent` is the single entry point for every payment-provider event.

- **Signature verification precedes everything.** `paymentProvider.handleWebhook(rawBody, headers)` (verify-then-parse) runs before any database read; a failure throws `InvalidWebhookError`, mapped to `400` by the route (`apps/api/src/routes/webhooks.ts`) without ever reaching business logic. The route registers its own raw-body content-type parser scoped only to itself (Fastify plugin encapsulation) specifically so a real provider's signature check — which depends on the exact bytes received — is never defeated by a re-serialized JSON parse.
- **Idempotency.** `PaymentEvent` is keyed `@@unique([provider, providerEventId])`; a second delivery of an already-`processedAt`-set event returns `"duplicate"` with zero additional side effects — proven by a real replay test (`apps/api/test/subscriptions.test.ts`, and unit-level in `packages/subscriptions/src/webhooks.test.ts`). A row that exists but has `processedAt: null` (a crash mid-processing) is retried, not skipped.
- **Out-of-order delivery (new this phase).** Most providers guarantee at-least-once delivery, not ordering. `Subscription.lastWebhookEventAt` records the `occurredAt` of the most recently *applied* event; an incoming event whose `occurredAt` is older than that is rejected as `"stale"` and never applied — so a late-arriving "past_due" cannot undo a newer "activated." When neither the stored nor the incoming event carries a timestamp (a provider that gives no ordering signal), the system falls back to plain arrival order, exactly as before this phase. Four dedicated tests in `packages/subscriptions/src/webhooks.test.ts` cover in-order application, the stale-rejection case, and the no-timestamp fallback.
- **Failed payments and refunds (new this phase).** `payment.failed` maps to `PAST_DUE` (the same status `subscription.past_due` already produced) — `canAccess` (`packages/subscriptions/src/entitlements.ts`) only ever grants access to `ACTIVE` subscriptions, so a failed charge denies access immediately, with no implicit grace period. `payment.refunded` maps to `CANCELED` — a refund revokes access outright rather than letting the subscriber keep access through a period they were refunded for. Both are covered by dedicated tests, including a refund-replay-is-a-duplicate case.
- **Cancellation.** `setCancelAtPeriodEnd` (`packages/subscriptions/src/subscriptions.ts`) tells the provider not to renew (required, not best-effort — a silent failure here risks charging again next period) but leaves access intact through the period already paid for; the provider webhook, not this call, is what actually flips `status` once the period ends.

## Database

Migration `20260907234804_phase15_hardening` (see `docs/architecture.md`'s Phase 15 section for the full list) adds:

- `Subscription.lastWebhookEventAt` (the out-of-order guard above) and `@@index([creatorId])` (dashboard/revenue queries were filtering by `creatorId` alone with no index whose leading column matched — see "Findings and fixes" above's cross-reference).
- A real foreign key from `ContentKeyGrant.subscriptionId` to `Subscription.id` (`onDelete: SetNull`), closing the referential-integrity gap described above.
- Three `CHECK` constraints mirroring existing application-level validation as defense-in-depth, not new business rules: `subscription_tiers.priceCents > 0`, `subscriptions.priceCentsAtSubscription > 0`, `media_assets.size > 0`. Prisma 5.22 has no stable `@@check` directive, so these are hand-written SQL in the migration rather than something `prisma migrate dev` would regenerate on its own.

## API-layer protections

- **Schema validation.** Every route accepting a body validates it with a `zod` schema before touching the database — this predates Phase 15 and was re-verified during the route audit above; nothing was found accepting unvalidated input.
- **Rate limiting** (new this phase). `@fastify/rate-limit`, Redis-backed (shared across API replicas, not per-process) via `@fastify/rate-limit`'s own `redis` store option. A global default (300 requests/minute per client, keyed by `x-forwarded-for` falling back to `req.ip`) protects every route; `POST /auth/atproto/start` gets a much stricter override (10/minute) because every call makes a real outbound request to a third-party PDS — a flood there is an attack on someone else's infrastructure via this one. `/health`, `/ready`, and `/metrics` are explicitly exempt (`config: { rateLimit: false }`) so a Kubernetes probe or a Prometheus scraper is never throttled into a false-negative reading.
- **Request size limits** (new this phase). `bodyLimit: 256 * 1024` (256 KiB) on the Fastify instance — every real request this API accepts (the largest is a post: ~10,000 characters of text, up to 20 media references, a handful of tags/langs) is well under that; media bytes never pass through this API at all (Phase 8's presigned-URL flow uploads straight to object storage).
- **Security headers** (new this phase). `@fastify/helmet`, registered with `contentSecurityPolicy: false` (this is a JSON API with no HTML rendering surface of its own — the web app's CSP is a separate PHASE 16 concern) and `crossOriginResourcePolicy: { policy: "cross-origin" }` (the web app is a different origin that legitimately fetches this API; helmet's `"same-origin"` default would fight the existing `@fastify/cors` configuration). Every other helmet default applies: `X-Content-Type-Options: nosniff`, `X-Frame-Options`, `Strict-Transport-Security`, `Referrer-Policy`, etc. — verified against a real running server (`curl -i /health`) as part of this phase's exit checklist.
- **CORS** (pre-existing): `@fastify/cors` with an explicit, configured `CORS_ORIGIN` allowlist and `credentials: true` — never a wildcard origin with credentials.

## Observability

See `docs/architecture.md`'s Phase 15 section for the full design writeup. In summary: structured (pino) logs with a request id on every line (pre-existing); `GET /metrics` (new — Prometheus exposition format, per-request duration histogram plus Node.js/process default metrics, its own isolated `prom-client` registry per process); `GET /ready` now checks **both** Postgres and Redis (previously Postgres only, despite Redis being a real hard dependency for sessions, OAuth state, and rate-limit counters); and an `ErrorReporter` interface (`apps/api/src/errorReporting.ts`) — the same dependency-injection seam as `PaymentProvider`/`MediaProcessor` before it — with a real, logging-based implementation (`LoggingErrorReporter`) that a future Sentry/Bugsnag/APM integration can replace with zero call-site changes.

## Independent security review (2026-09)

A full-application security review (not tied to a `prompts/full.md` phase) covering every service in this monorepo — `packages/auth`, `apps/api` route handlers and `packages/database` query construction, `packages/subscriptions` webhook handling, `packages/media`, `packages/moderation`, `apps/web`, `packages/atproto`/`packages/content`/`packages/discovery`/`packages/shared`, `infrastructure/kubernetes`, `infrastructure/docker`, and `.github/workflows` — found **no high-confidence application-layer vulnerability** in the categories a security engineer would flag as a PR blocker (auth/session bypass, IDOR, injection, SSRF with attacker-controlled host/protocol, forgeable webhooks, path traversal, hardcoded secrets, XSS via unsafe DOM sinks, overly-broad Kubernetes RBAC). This reflects the Phase 15 hardening pass and the two post-review fix rounds already in this codebase's history, not new findings — see the rest of this document and `docs/threat-model.md` for what was specifically verified.

### Dependency vulnerabilities — one real gap, patched; one tracked and deferred

`pnpm audit --prod` found 27 advisories, **all** in `next` (and its bundled-and-pinned `postcss` dependency) — nothing in `apps/api`'s dependency tree or any other package.

- **Fixed:** `next` was pinned to `^14.2.18`, which predates the last several security releases on the 14.x line. Bumped to `^14.2.35` (the latest 14.x release; a major-version jump to 15/16 was deliberately not taken — see below). This alone did not move `postcss`, since Next.js hard-pins its own internal copy (`postcss@8.4.31`, vulnerable to GHSA-fxqj-rqcc-2cmp / GHSA-7fh5-64p2-3v2j — arbitrary `sourceMappingURL` file read); closed with a `pnpm-workspace.yaml` `overrides` entry forcing it to `>=8.5.26` (safe: postcss 8.x is semver-stable across this range, and this app's own direct `postcss` devDependency was already on a patched version). `pnpm audit` confirms zero `postcss` advisories after the override.
- **Mitigated without a version bump:** two of the remaining advisories are CRITICAL unauthenticated-RCE reports against Next.js's built-in Image Optimization API (`GHSA-p293-qw3h-jr36`, Windows-hosted servers only — this app deploys exclusively on `node:22-bookworm-slim` Linux containers, so not applicable; `GHSA-2xp9-vwfh-vxw4`, AVIF handling — this app never uses the `next/image` component or configures `images.remotePatterns` (avatars/media are plain `<img>` tags against signed URLs/the creator's own PDS), so there's no path for an attacker to get their own image bytes through the optimizer even before patching). `apps/web/next.config.mjs` now sets `images: { unoptimized: true }` regardless, closing the route as an attack surface outright rather than relying on that reasoning holding forever.
- **Remaining, deferred:** the rest of the advisories (several Next.js Denial-of-Service reports against Server Components/Server Actions, and framework-level SSRF reports in WebSocket-upgrade handling, Server Actions on custom servers, and Next's own rewrite-resolution code) have no fix backported to the 14.x line — only `>=15.5.x` carries them, per each advisory's own patched-version range. This app doesn't use Server Actions, WebSocket upgrades, i18n routing, or a hand-written custom server (checked directly — no `"use server"` directives, no `WebSocket`/`ws://` references, no `i18n` config, no `pages/` directory), which rules out most of these as live attack paths; the rewrite-resolution SSRF report is framework-internal (a parsing flaw in how Next resolves *any* configured rewrite, not specific to this app's own fixed, non-attacker-controlled `destination`) and is the one genuinely unverified residual risk. Closing it fully requires the Next.js 14→15 major-version upgrade, which changes several App Router APIs (`cookies()`/`headers()`/route `params`/`searchParams` become `Promise`-returning) across dozens of files in `apps/web` — too large a change to make correctly, and to verify as correct, within this review. Tracked as follow-up work; see `docs/threat-model.md`'s "Accepted risks" and `docs/production-readiness.md`'s "What remains open."
- Verified after the fix: `pnpm --filter @foryour-fans/web typecheck`, `pnpm --filter @foryour-fans/web build`, and the full `apps/web` test suite (274 tests) all pass unchanged.
